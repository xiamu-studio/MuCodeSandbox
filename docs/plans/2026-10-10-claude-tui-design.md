# Interactive Claude Code acceptance

Run the real Linux CLI without `-p`, permission bypasses or a blanket tool allow
list, in the application's production web terminal. Use a disposable strict
transparent VM, an isolated guest configuration directory and the fixed
synthetic Messages credential. Do not share host credentials or log in.

The setup proxy may download dependencies but denies provider domains. Close
all setup sockets before switching to a fixture-only allow list. During tasks,
the only permitted proxy destination maps to the local Messages fixture.

Acceptance requires actual rendered terminal screens and server-side receipts:

1. Open the actual interactive prompt. Fresh account onboarding is a separate
   gate: the first real run attempted a hardcoded provider connectivity check
   and was correctly blocked by the local-only network. The fixture now uses
   the documented `IS_DEMO=1` option to skip onboarding and
   `ANTHROPIC_AUTH_TOKEN` for its synthetic local gateway credential.
2. Reject Write through its actual permission menu and prove the file remains
   absent. Start another turn, approve Write and inspect the real Write / Read /
   Bash results. The client's ordinary policy permits the read-only Bash
   command; a separate Bash write requires a genuine permission prompt.
3. Cancel a streaming response, observe the server connection close, and submit
   another turn in the same live CLI process.
4. Exit, reopen with the CLI's normal continuation option, and complete another
   interactive turn. Verify previous prompts are in the actual resumed API
   request. Merely launching another print-mode command does not count.
5. Reject a direct physical-interface bypass, compare protection fingerprints,
   and preserve the physical egress capture with positive approved-proxy traffic
   and no unapproved output packets.

Keep failed runs and their screenshots separate from successful evidence.
Source web-terminal results do not prove packaged Electron, provider-account,
all tools, all versions, desktop integration or residential-line acceptance.

## Packaged acceptance

Use the same interactive workflow against the actual signed local candidate's
native PTY. Start the real Electron executable with independent app and user
data directories. Create a fresh protected VM and cold-install the CLI through
the packaged API. Source runtime calls only prepare synthetic files and observe
guest processes or captures; they must not launch the CLI for the application.

Inspect the actual package identity, window isolation preferences and renderer
OS sandbox status. Observe application-owned limactl and ssh with real TTYs.
Close the terminal pane while leaving the main window open, then prove those
host processes and the guest CLI exit, the response disconnects and protection
remains active. Preserve original packet bytes and independently audit the
package, source, artifact manifests, receipts and physical-interface traffic.

The packaged report is separate from source evidence. First account onboarding,
WireGuard TUI, arbitrary detached descendants and other package workflows remain
separate acceptance gates.

## WireGuard Acceptance

Run the same workflow in the actual Electron package against a fresh client VM
created and cold-installed through the packaged API. A separate disposable Linux
VM terminates the real kernel WireGuard tunnel. Its synthetic target address
relays bytes through an owned reverse SSH connection to the loopback Messages
fixture; no model account or credential is required.

Dependency downloads may use gateway forwarding during installation. Before any
interactive CLI starts, install forward-chain drop rules in both directions for
the client's tunnel address. Prove external HTTPS fails, the local fixture still
responds, and gateway connections originate from the client's tunnel address.
Use a duplex relay so cancellation closes the actual response without a timed
buffer masking it.

Retain separate first-boot and interactive-task captures with actual interface
index, byte count and SHA256. Independent protocol filtering must find only the
approved peer UDP endpoint plus explicit management SSH and DHCP exceptions.
Require positive tunnel traffic and first-boot DHCP evidence. This proves the
local two-VM path, not a real public/residential peer, long-duration operation,
host sleep/network switching or every CLI tool and fault mode.
