# Windows 虚拟磁盘压缩中断恢复研究

状态：研究方案，未接入产品，未执行真实压缩。

当前实现通过 Hyper-V 的 `Optimize-VHD` 提交离线压缩。代理断开或超时后，供应程序可能仍在后台运行；受保护记录处于 `compacting` 时不能仅因代理退出、任务查无结果或发出取消请求而释放围栏或重复提交。

微软的 [`CompactVirtualDisk` 文档](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-compactvirtualdisk) 对另一条底层 API 路径明确指出，虚拟磁盘压缩可以安全中断并在之后重新执行；不传异步参数可同步调用。文档同时说明未挂载的文件系统无关模式按全零块回收，这与现有客体 TRIM 加 `Optimize-VHD -Mode Pretrimmed` 的效果不应直接视为相同。

这为替代实现提供候选，但“中断后可以重做”并不证明旧请求已经终止。尤其是 [`CancelIoEx` 文档](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex) 说明取消请求并不等待 I/O 完结；不能把取消请求、客户端断开或句柄消失直接作为操作完成回执。尚未找到足以证明进程异常退出后该 API 的底层操作已终止的依据，也没有证明其与 Hyper-V 后台任务互斥。

后续实现和实机验证需要依次确认：

1. 用独立、专用的合成 VHDX 验证 API 的打开方式、动态盘身份、无父盘、只处理目标、空间变化和文件读回；不同模式的可回收效果分别记录。
2. 设计受保护的执行者、磁盘身份与互斥证明，明确请求提交前后、控制进程退出、取消以及宿主重启时如何证明原操作已终结。无法证明时继续保留围栏。
3. 验证中断后可恢复、不能并发提交、恢复后的客体可启动且测试文件完整；不能把成功返回或占用变化当成文件完整性证明。
4. 完成上述验证前，保持现有压缩产品入口关闭；保留现有 VM、用户磁盘与备份。

现有 3 GiB 空间不足验收盘的授权只覆盖其原方案，不能自动扩大为此压缩实验的修改许可。

## 独立空 VHDX 的底层接口探测（2026-10-28）

按用户要求优先推进空间回收，在 Codex 工作区新建了专用 1 GiB 逻辑容量的空动态 VHDX，初始文件占 4 MiB，未挂载、未格式化、没有用户数据。普通权限下 Hyper-V 的 `New-VHD` 因权限拒绝且未创建文件；直接调用 Windows `CreateVirtualDisk` 成功创建该独立测试盘。用 `OpenVirtualDisk` 的 `VIRTUAL_DISK_ACCESS_METAOPS` 打开后，同进程第二次打开返回 32（共享冲突）；在首句柄上同步 `CompactVirtualDisk` 返回 0，关闭后重新打开返回 0，文件长度仍为 4 MiB。脚本和测试盘位于 Codex 工作区 `work/compact-native-create-probe.ps1`、`work/compact-native-empty-probe.ps1` 和对应 `compact-native-synthetic-57e772fc03c34c119fa16bba00e7ce9a.vhdx`，均保留。

该结果只证明一张空盘上一次同步调用和两个同进程句柄的冲突；没有模拟 Hyper-V 后台任务、进程崩溃、重启，也没有验证非零数据回收或文件系统读回。它不证明其他进程或 WMI 操作已经结束，不能解除现有 compacting 围栏，也不构成产品功能交付。参考微软 [OpenVirtualDisk](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-openvirtualdisk) 与 [CompactVirtualDisk](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-compactvirtualdisk) 文档。

继续在同一空合成盘用独立进程持有 METAOPS 句柄：主进程打开返回共享冲突 32；终止持有句柄的专用测试子进程并确认退出后，主进程重新打开返回 0，文件仍为 4 MiB。证据脚本为 Codex 工作区 `work/compact-native-process-probe.ps1`。持有进程当时没有提交压缩，故此结果仅证明该场景的跨进程排他与进程退出后句柄释放，**不能证明压缩途中进程退出后底层操作已结束**，仍不解除未知结果围栏。当前进程没有 `SeManageVolumePrivilege`，没有现成的 `qemu-img`/`qemu-io` 或 WSL Linux 发行版，尚未生成含测试数据的盘并验证空间回收。

随后使用 `CreateVirtualDisk` 新建 32 MiB 固定格式合成 VHD，在固定盘原始数据区写入 1 MiB 合成内容，借助 Windows 的来源复制接口生成 VHDX；没有挂载、分区、文件系统或真实用户数据。将 VHDX 分别在压缩前和压缩后复制回独立固定 VHD，三个磁盘的完整 32 MiB 逻辑数据 SHA-256 均为 `2bb15954e9effad8108350a41e8660e8112661a2956b7b0a685a1570dbb31288`，源固定盘完整文件摘要保持；`CompactVirtualDisk` 返回 0，但 VHDX 文件长度前后均为 37,748,736 字节，未观察到文件长度缩减，也未测量前后宿主实际分配量，故不能宣称释放空间。此无文件系统合成例子不能代表 Linux TRIM 或真实负载。脚本为 Codex 工作区 `work/compact-native-data-probe.ps1` 和 `work/compact-native-data-verify.ps1`，合成源、目标及两份读回盘均保留。下一步需验证实际分配量、真实释放和异常恢复，再考虑连接产品。

追加两次独立同内容合成盘实验并通过文件压缩大小接口测量宿主分配：默认块大小时 VHDX 文件长度和分配均为 37,748,736 字节，压缩前后无变化；创建 VHDX 时显式设为 1 MiB 块时，复制完成后长度及分配即为 5,242,880 字节，压缩前后仍无变化。两种情况压缩前后完整逻辑内容均匹配源数据，原固定源摘要保持。第一次 1 MiB 块试验被旧测试脚本的精确长度保护拒绝后，核对确切新盘并扩展允许的合成长度才继续；没有修改产品保护。这证明合成复制过程中块配置影响占用，但没有证明对现有 VHDX 的删除空间可回收，不应将它当成用户虚拟磁盘缩减成功。

进一步对新建的专用 1 MiB 块合成 VHDX 做受限空间回收：源固定盘有两块不同合成内容；验证目标文件中第一块的完整内容、唯一性和 1 MiB 对齐后，直接把该块的 VHDX 文件载荷置零，模拟可回收零块，第二块保留。通过 Windows 磁盘复制接口在压缩前和压缩后分别读回完整 32 MiB 逻辑内容，二者均与预期 SHA-256 `1166015d8e50a13df42a466bcf867c78fc671e2b6682c6bc7c5396d88abd697e` 一致，固定源完整文件摘要保持。同步 `CompactVirtualDisk` 成功，VHDX 文件长度及实际分配均从 6,291,456 降至 5,242,880 字节，回收 1,048,576 字节。脚本为 Codex 工作区 `work/compact-native-reclaim-probe.ps1`，专用源、目标和读回副本保留。

此结果证明底层 API 可对人为置零的完整 VHDX 块实际回收并保留其余逻辑数据；人为直接改写测试 VHDX 载荷只是构造零块的手段，**不是产品实现或 Linux 文件删除/TRIM 的验证**。未验证正在压缩时的进程退出或 Hyper-V 后台任务互斥，不改变已有围栏和用户入口关闭状态。

## 异步提交后终止测试进程（2026-10-28）

另建一张同规格独立合成盘并构造同样的零块，先完整读回预期逻辑数据。测试子进程调用异步 `CompactVirtualDisk`，API 返回 `ERROR_IO_PENDING`，随后使用同一 OVERLAPPED 调用 `GetVirtualDiskOperationProgress`，确认其操作状态也是 `ERROR_IO_PENDING` 后发出标记；父进程收到标记后立即终止该专用子进程并确认退出。随后另一个进程重新获取 METAOPS 句柄成功，将盘复制为固定 VHD 后完整读回逻辑数据，SHA-256 与预期 `1166015d8e50a13df42a466bcf867c78fc671e2b6682c6bc7c5396d88abd697e` 一致；源盘摘要不变，没有再次调用压缩。

进度报告与进程被终止之间存在时间间隙，**无法证明终止的瞬间操作仍在进行**；该结果也不证明 Hyper-V 的 `Optimize-VHD` 后台 WMI 任务已结束，不能用来解除现有 compacting 围栏或宣布中断恢复完成。相关代码和合成盘在 Codex 工作区 `work/compact-native-async-holder.ps1` 与 `work/compact-native-reclaim-probe.ps1` 中；进度状态定义见微软 [GetVirtualDiskOperationProgress](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-getvirtualdiskoperationprogress) 和 [VIRTUAL_DISK_PROGRESS](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ns-virtdisk-virtual_disk_progress)。

## Hyper-V 存储作业回执候选（2026-10-28）

微软 [CompactVirtualHardDisk](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/compactvirtualharddisk-msvm-imagemanagementservice) 的 WMI 方法支持 Pretrimmed（模式 3），异步提交返回作业引用；同步完成可返回 0。它可能比目前通过 `Optimize-VHD` 子进程只能等待整体返回更容易记录可复查的作业身份。当前普通权限对本机 `Msvm_StorageJob` 做只读查询没有返回现存作业；空列表不能证明管理员调用、创建作业、作业查询权限或压缩已结束。

关键限制：提交调用成功与应用持久保存作业引用之间仍有崩溃窗口；[Msvm_StorageJob](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-storagejob) 作业按文档默认仅保留完成后五分钟，`DeleteOnCompletion` 为只读，因此查询不到作业不能解释为已完成或已终止。[CIM_ConcreteJob](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/cim-concretejob) 说明 Killed 状态可能仍留后台进程，不能把其当成终止证明。更不能仅凭查看到一个无关作业放开原磁盘围栏。

可继续设计的路径是受保护进程先保存目标身份和提交意图，直接提交 Pretrimmed，将实际返回的作业引用绑定并持久化，然后只对该引用核验状态、错误码、原目标磁盘身份和原 VM 停止状态；明确成功后仍要走既有客体重启和几何核验。若作业引用未能持久保存、作业过期/查询失败、后台操作状态不明确或作业是 Killed，一律保持 `compacting` 围栏。该候选不能独自解决提交/回执窗口、凭作业引用可靠证明目标、系统重启时 provider 行为或真实 Linux TRIM 问题；尚无代码实现、管理员测试或真实磁盘操作，不能据此开放产品入口。

## 固定作业提交与查询原语（2026-10-28，源码未接线）

基于前述真实空合成盘 WMI 结果，在 Hyper-V 固定脚本新增实验性 `compact-disk-submit` 和 `compact-disk-job` 原语：提交前复核受保护 VM、关闭状态、动态无父盘 VHDX、容量及磁盘 GUID，固定使用 Pretrimmed；同步完成返回独立回执，异步返回规范化的 StorageJob GUID。只读查询要求准确 GUID、唯一匹配、作业类型为 Compaction（3）且状态、错误码与完成 HRESULT 均存在，返回原始有限状态供未来受保护协调器判断；没有将失败、消失或超时当成完成，也没有取消或重试作业。作业类型及完成码定义见微软 [Msvm_StorageJob](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-storagejob)。

受控 PowerShell 夹具验证同步、异步、未返回身份、非独立盘、无权限标志、作业缺失、错误身份、错误类型和缺少状态或完成码等情况；连同既有压缩和受保护事务测试共 3 项通过，均为模拟 provider。上述动作尚未接入 broker 的持久作业编号或恢复操作，也没有在该新实现上调用真实 Hyper-V；现有产品仍使用原先的受限路径且入口关闭。提交成功但记录 GUID 前进程崩溃仍保持未知结果，需要永久保留围栏；真实 Linux TRIM 和实际回收也未完成。

## 受保护作业编号与续查事务（2026-10-28，源码未安装、入口关闭）

实验性磁盘维护路径已从等待 `Optimize-VHD` 整体返回改为固定的 WMI Pretrimmed 提交：代理在调用前持久写入 compacting 围栏；同步成功继续核验，异步取得规范 StorageJob GUID 后将它写入受保护双副本登记，再查询该准确编号。只有 JobState 7、ErrorCode 0、JobCompletionStatusCode 0 且作业类型为压缩时，才重新核验原 VM、磁盘 GUID、文件身份及容量并转入 verifying；仍需独立维护启动、客体几何核验和确认停机才可完成。作业仍运行、失败、查询不到、返回字段不完整或身份变化时，保留 compacting，不重新提交。若提交成功但引用未返回或未成功持久化，仍无法确认，保留原围栏；WMI 作业记录过期也不会被当作成功。

因此此机器的这次实验没有提供从受影响磁盘反查原作业的证据；不能把空关联、唯一存储作业或等待时间当作作业已完成，也不能解除围栏。下一步需要在提交后尽早持久记录原作业回执；即使这样仍须保留提交与持久化之间的未知状态，不能宣称该边界已解决。

## 提交回执提前持久化（2026-10-28，源码未安装）

受保护代理现在在提交前把唯一操作编号写入 compacting 登记，并准备专用受保护回执目录；固定 Hyper-V 脚本取得 WMI 返回后，将操作编号、VM 和磁盘身份与准确作业编号写入新文件，刷新后原子发布，再返回代理。代理重启后如果登记中还没有作业编号，可读取该回执，核对目录与文件权限、单一文件身份、长度、操作编号、原 VM 和磁盘身份，再保存编号并继续查询原作业；明确同步完成的回执也要经过后续磁盘身份和客体核验。回执缺失、未完成、内容异常、身份不符或 WMI 作业不可查询时继续保留围栏，不重复提交。状态显示在存在操作编号但登记暂缺作业编号时允许尝试核查回执，不断言能恢复。

受控脚本检查覆盖异步和同步回执、重复文件及无效编号在提交前拒绝；原生事务模拟检查覆盖有效回执接续与错盘拒绝，真实 Windows 命名管道和保护登记检查通过，代理编译通过。另在工作区空合成 VHDX 上执行真实 WMI 和固定脚本回执发布，回执与返回的作业编号一致、盘摘要不变，证据 outputs/compact-wmi-receipt-proof.json；该实验的 VM/Get-VHD 身份审阅及目录权限为合成条件。没有在受保护真实 VM 上强制终止进程验证此新路径，提交到回执发布之间的崩溃窗口和 WMI 记录过期仍无法自动确认。当前安装版 preview.74 不含本次原生修改，回收入口继续关闭。

补充主路径核对：回执异步作业与同步完成两种情况均可进入后续验证，错盘回执和缺失回执保留原围栏；相关原生事务、管道和提交适配共 4 项通过。代理重启后仍需核验真实作业或后续客体，不能把回执文件存在本身当作最终完成。

## 回收回执在正常流程中核验（2026-10-28，源码未安装）

为避免只在异常重启后才发现回执权限或身份错误，压缩提交正常返回时，受保护代理也读取持久回执、核对目录和文件保护、操作及磁盘身份，并确认回执与提供程序返回的完成状态和作业编号一致；不一致或回执缺失时保留维护围栏，不报告完成。重新读取已有作业编号时不会重复写入登记，不改变未确认时不重复提交的原则。

Windows 命名管道和原生事务定向检查通过，覆盖缺失回执、回执与返回不符时保留围栏；完整原生代理用 Windows PowerShell 编译通过。检查使用合成代理，尚未验证实际受保护目录权限；当前 preview.75 不含此修改，回收入口仍关闭。
