# Windows 原盘显式登记恢复

普通启动仍拒绝“两份受保护登记均丢失但 VM 数据仍在”的状态。专用恢复入口可以检查当前普通用户 SID 下已有、已停止的受保护 VM，并在审阅确认后重新登记；它不复制、重建、启动、停止或删除 VM 和磁盘。

## 当前支持边界

- 只处理 `ProgramData` 固定受保护目录中属于当前用户的未登记分配，不接收任意源目录、目标路径或其他用户 SID。普通应用须关闭，恢复进程使用同一份会话互斥。
- 要求原 Hyper-V VM、专属 Private 交换机、双向全 IP 拒绝规则、固定网卡策略、独立原盘和种子文件都完整，且 VM 为 Off。缺少资源、网络规则变化、快照、父盘、共享磁盘、动态内存和不符合资源范围的配置会拒绝；恢复入口不修复这些对象。
- 需要原环境配置中的镜像摘要，以及同摘要的既有受保护缓存文件。摘要用于恢复原配置引用，不会把缓存镜像覆盖到原磁盘，也不等同于对旧客体全部系统文件的重新审计。官方构建源摘要不可用于此入口，构建器恢复继续使用组件准备流程。
- 审阅分别计算原磁盘、种子文件、缓存镜像与登记副本的摘要，核对前后 VM 身份和配置。发布时重新执行核验；审阅后资源变化或名称确认不匹配会拒绝。
- 文件句柄在核验与发布期间阻止磁盘、种子和镜像被写入或替换。目录联接、文件重解析点、硬链接、非受信任权限和所有者均拒绝。
- 读取阶段不创建或修复登记。显式发布前归档所有既有登记原件，再写双副本。即使原 JSON 损坏也保留原始字节；同代次有效副本冲突、权限异常仍需管理员诊断，不能用恢复模式绕过。
- 恢复会话只允许握手、审阅、一次登记发布和关闭。发布后仍不能启动 VM、打开管理通道、删除资源或安装 Windows 组件；需关闭恢复入口后重新打开正常应用。启动后的权限与联网仍经过正常防护核验。
- 原普通用户侧管理密钥和配置仍需存在，恢复登记不会生成替代密钥或重置客体。旧管理员入口中的用户可写盘迁移、其他账号间迁移、仅剩磁盘而 VM 配置也丢失等场景继续独立实现。

VM 文件的权限核验单独处理 Hyper-V 自动添加的 VM 服务权限；登记和缓存仍只接受管理员/SYSTEM。目标 VM 服务身份按已核验 GUID 解析，服务组仅在目录上接受受限的读取/创建权限，当前验收系统的 worker capability 使用固定 SID，未知 capability 或其他 VM 身份均拒绝。微软分别说明了 [VM 专属 SID 对磁盘访问的作用](https://learn.microsoft.com/en-us/troubleshoot/windows-server/virtualization/hyper-v-virtual-machine-not-start-0x80070005) 和 [VMMS 管理的 Virtual Machines 服务组](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers)。不同 Windows 构建的 worker 权限继续纳入第二系统兼容验收。

## 源码预览入口

以下命令在仓库中使用配套 Node 运行。先关闭 Windows 桌面程序；以普通用户启动，由 Windows 显示受限代理的管理员确认。首次更新代理时可给 `review` 命令增加 `--install-broker`。

```powershell
node scripts/windows-recover-storage.ts review --id <原环境UUID> --image-sha256 <原镜像SHA256> --review <新审阅文件.json>
```

检查输出中的 VM 名称、原 Hyper-V GUID、CPU、内存、容量与摘要。输出不含用户名、SID、磁盘路径、出口 IP 或管理密钥；审阅文件仍应仅在本机保存。取消或只执行上述命令均不恢复登记。

确认恢复该对象后，使用审阅中完整的 `mu-win-…` 名称：

```powershell
node scripts/windows-recover-storage.ts adopt --review <审阅文件.json> --confirm-name <完整VM名称>
```

成功后 VM 继续为 Off，磁盘保留。重新打开普通应用后，使用原环境配置和管理密钥恢复连接。此入口目前供源码预览操作；桌面恢复向导仍待接入。
