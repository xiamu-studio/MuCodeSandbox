# Windows 持续运行验收

`preview.10` 已完成独立 Pro/Linux 的完整 45 分钟验收：45.01 分钟、90 个成功回合及 13 项真实检查通过，原盘重启读回、实际进程回收和资源清理均已独立核验。此前 `preview.8` 的云代理路由扰动和 `preview.9` 的 SSH 诊断混入数据失败记录继续保留，不把它们的时长拼入本次结果。跨夜与更多故障组合仍待验收。

## 运行范围

真实普通用户控制器、受保护 Hyper-V 代理和一台独立 Linux，持续保持同一联网会话。计时从 Linux、联网许可和长连接就绪后开始，目标完整 45 分钟，不能通过参数缩短。

- 一条实际 TLS 连接每秒发送有序记录，客体 `dev` 进程核对测试身份和连续序号；每轮读取客体进度，不能只依据接收端写入计数认定客体存活。
- 目标每 30 秒执行一轮：核对会话和有效联网许可、真实本地 DNS/HTTPS 请求、64 KiB 合成文件上传、列表版本检查与逐字节下载比对。保留每轮时间、许可余量、客体序号、Node 内存和活动资源数量。
- 累积文件分页核对，无重复或遗漏。结束后取消长连接，并以客体 PID 和内核启动标识确认实际进程回收。
- 确认停机后以新会话启动原盘，核对首个和最后一个文件的摘要，再删除本次专属资源。

每轮完整使用生产权限核验，不能为提高吞吐而绕过核验。首轮观察到每轮约 22 秒，因此原定 10 秒节奏不适合此串行链路；该校准运行已主动取消、确认进程退出及 VM 停止，原输入、代码、进度和结果保留。通过新的普通控制器和受保护代理，仅清理已独立核对的原停机资源，之后使用新案例重新计满 45 分钟，未将校准时长拼入新运行。

## 通过条件与证据

`scripts/windows-pro-soak-evidence.ts` 要求：实际连续计时至少 45 分钟、至少 80 个成功回合、回合间隔及操作耗时不超过 45 秒、同一持久连接的客体序号持续前进、所有文件读回与分页检查通过、实际客体进程回收、原盘重启读回及资源清空。内存数据用于观察趋势，这一时长不证明不存在长期内存泄漏。

当前结果包含 13 项真实检查、控制器与代理的实际退出确认；结束后独立核查 VM、专属交换机、登记及运行目录为零，登记副本相同。9 个后端文件与实际包载荷、本地编译产物、初始绑定逐一比对，并核对诊断源码、物理宿主启动时间与远端 `main`。任何缺失、失败或仍活动的运行都不能标为通过。

准备命令为 `node scripts/windows-pro-soak.ts`，已有案例禁止直接重跑。`windows-pro-probe.ts` 提供 `soak-stage`、`soak-run`、`soak-inspect`；观察超时后继续检查原进程，不能重新启动同一案例。`soak-cancel` 只停止身份、磁盘、登记和所有者匹配的测试 Linux；`soak-retire` 仅适用于已确认退出并保留了失败结果的原停机案例，使用另一个受限控制器执行生产删除路径。新案例的 `--after-retired-case` 要求清理结果及之后的零资源观察，并保留原输入归档。

运行结束后先执行 `soak-inspect` 和 `collect-state`，再运行 `node scripts/windows-pro-soak-evidence.ts`。不能把 `soak-inspect` 本身成功或计时器启动视为整轮成功。

接收端、DNS 和代理都在本机回环；只映射保留测试地址，其他目标拒绝。没有 AI 网站、外部翻译服务、Windows 系统剪贴板、真实账号或物理宿主重启。外层 Pro 保持运行且网卡断开。物理切网与实际休眠、跨夜运行及其他故障组合继续单独验收。

## 当前失败与保留证据

已取得 59 个成功回合、一条持久连接和 1765 条接收端写入记录，随后生产 `assertAccess` 失败，原控制器、代理退出，原 VM 独立确认 Off。成功回合中的活动资源数量有所增加，但现有记录没有资源类型明细，尚不能据此认定泄漏原因。

只读 SQLite 与磁盘解析没有改动原数据，磁盘检查前后 SHA-256 相同。客体日志显示 `walinuxagent.service` 在首次启动约 1800 秒后放弃云配置等待，重新进行 DHCP/路由检查，与失败时点接近；这些初始记录仅构成待验证关联，后续受控复现见下节。没有本轮对应的原生电源/资源栅栏回执；较早的低磁盘记录属于另一案例，不能移用作本轮原因。

未重新启动或修复失败原盘。归档程序已保留原 VHDX、管理身份、DPAPI/SQLite、登记及诊断报告，并按字节摘要核对；元数据复制对隐藏的系统祖先目录显式使用 `-Force` 读取属性，恢复阶段只补齐缺项或核对已存在副本，不覆盖不匹配文件。完成归档后才通过受保护代理删除原测试分配，独立检查确认 VM、专属交换机、登记和运行目录为零；原盘副本继续保留。此处是受限测试机内的合成数据诊断归档，不是产品加密备份功能。

归档阶段还发现调度遗漏：新阶段未进入专用处理器，误入旧初始验收入口，改写了测试机代理选择并留下一个失败任务。已保留修复前元数据、恢复已知代理摘要并移除该任务，原 VM 保持 Off、登记字节未改变。调度器现为 `soak-*` 独立分发，且初始验收前有仅允许四个历史阶段的失败关闭检查；新增实际 PowerShell 回归覆盖 `soak-preserve` 等阶段不能进入旧安装路径。后续诊断阶段不能再通过默认分支启动系统准备。

`scripts/windows-pro-soak-failure-evidence.ts` 已独立核对 59 轮、原盘只读前后摘要、完整归档、代理恢复及最终清理，5 个实际后端文件仍与当时 `preview.8` 载荷和本地编译产物一致；宿主启动时间和远端主线不变。输出明确为 `complete:false, evidenceVerified:true`，这份初始失败证据生成时根因尚未确认。官方 [Azure DHCP 处理代码](https://raw.githubusercontent.com/Azure/WALinuxAgent/master/azurelinuxagent/common/dhcp.py) 包含路由配置职责，但仅凭关联日志还不能断言它就是这次核验失败的直接原因。由此开展下节受控复现，并保持原有失败关闭策略。

## 受控复现与 preview.9 修复

后续新案例使用未修改的 `preview.8` 载荷及同一固定图形基盘，运行客体中已安装 Azure agent 的真实 DHCP 准备函数。诊断只包裹实际广播路由添加方法以记录内核路由差异，在该方法执行后中断，未进入 DHCP 数据报发送步骤。新增加的条目为 `255.255.255.255 dev mu_tun`；生产完整性摘要随即改变，而许可仍有效，原活动会话关闭并确认停机。原 VM 和登记清理后，4 项真实检查及 6 个执行文件摘要绑定通过。它验证了上述 1800 秒日志对应代码路径可导致同类中断，不代替修复后的完整持续测试。

修复仅位于 Windows 客体实现：NoCloud 启动、空白基盘准备和每次运行准入均停止并持久屏蔽 `walinuxagent.service` 与 `waagent.service`，核对屏蔽状态、活动状态及主进程为零。完整性检查还验证 root 所有的 `/dev/null` 屏蔽链接和服务状态，不能通过重新启用代理绕过。没有把额外路由加入允许列表，也没有放宽原有防火墙、许可期限或失败关闭策略。Mac 客体与发布架构不变。

Windows `0.4.66-preview.9` 未签名测试包已构建，审计 5637 个文件、169 个代码文件，无本机路径或运行私密文件；Windows 自动测试 222 项通过。真实 Pro/Linux 已通过云代理关闭、新建文件夹、同名拒绝、普通 dev 身份与 0700 权限、符号链接、同文件系统绑定挂载、可写但非 dev 所有的目录、16 层上限及取消迟到确认的前置检查。

第二轮保留了 7 项真实前置检查，包括文件夹功能和云代理状态；其原盘、管理身份、数据库及日志已完成校验归档，原测试分配清理。`scripts/windows-pro-soak-checkpoint.ts` 明确记录 `complete:false`，并把文件夹检查通过与持续运行失败分开。

## preview.10 的 Windows SSH 输出分离

Windows OpenSSH 偶发把 socket 关闭诊断写入 stderr，远端命令仍以零状态成功结束。原 Windows 管理入口复用合并 stdout/stderr 的进程执行器，因而把该提示追加进 HTTPS 正文；严格比对按预期中止测试。`preview.10` 增加 Windows 专用 SSH 执行器，仅返回 stdout，逐通道解码 UTF-8，stderr 仍可由进度回调观察；非零退出仍报错。数据上限、取消与超时仍会停止进程，完成以实际子进程关闭事件为准。共享进程执行器及 Mac 路径没有修改。

新增 5 项实际子进程回归覆盖零状态诊断分离、分块 Unicode、二进制 stdin、非零退出、取消、超时和输出上限；Windows 全套 227 项通过。未签名 `preview.10` 安装包审计 5638 个文件、170 个代码文件，无本机路径或运行私密文件。

新案例绑定 9 个当前后端文件，并在完整前置检查及持久 TLS 就绪后重新计时；增加真实 Windows SSH 的 stdout/stderr 与非零退出核对，最终原盘重启读回文件夹。独立证据程序已确认 45.01 分钟、90 次连续成功的 DNS/HTTPS 与 64 KiB 文件上传下载、单条 TLS 连接、完整分页、真实 PID/内核启动标识回收、新会话原盘读回及最终清理。

进程 RSS 从约 59.2 MiB 到 51.6 MiB，观测峰值约 59.2 MiB；堆使用峰值约 28.0 MiB。Node 的 TCP 包装句柄统计随回合增加，但两次只读系统快照均只有 6 条已建立的回环连接，不能把包装句柄数等同为网络连接泄漏；更长时观测仍保留。整轮无失败回合，源 VM、交换机、登记和运行目录均为零，控制器和代理退出；本机启动时间、远端主线不变，没有访问 AI 网站或外部翻译服务。

本轮运行的是从审计后的 `preview.10` 载荷暂存的生产后端，没有操作 Windows 安装向导、真实输入法或物理扬声器。之后开发的文件管理器入口仍是源码阶段，不混算为此包的已验收功能。
